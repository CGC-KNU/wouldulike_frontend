# 마일리지 시스템 종합 정리

마일리지는 **원장(append-only ledger) + 잔액 캐시** 구조로 동작한다. 모든 적립·차감은 `mileage/service.py:apply_delta()`라는 단일 진입점을 거치며, 잔액(`MileageAccount.balance`) 갱신과 이력 기록(`MileageEvent` 생성)이 하나의 DB 트랜잭션 안에서 함께 일어난다.

- 관련 앱: `mileage`, 연동 앱: `coupons`, `missions`, `promotions`, `dashboard`
- DB: `coupons`/`mileage`/`promotions`/`missions` 모두 같은 물리 DB alias(`"cloudsql"`)로 라우팅된다 (`wouldulike_backend/db_routers.py`).
- 최종 정리일: 2026-08-31 (100포인트 개편 + 대회 멀티 티켓 반영 버전 + **프론트엔드(Flutter, `new1` 레포) 연동 점검 및 수정 반영**)
- ⚠️ 이 문서는 백엔드 레포 기준 문서다. 아래 §9는 프론트엔드(`new1`) 레포에서 실제 코드를 확인해 추가한 점검 결과이며, 2026-08-31에 그중 3건을 프론트 코드로 직접 수정했다(§9 각 항목 상단 상태 참고).

## 1. 데이터 모델 (`mileage/models.py`)

### `MileageAccount`
| 필드 | 설명 |
|---|---|
| `user` | User와 1:1 |
| `balance` | 현재 잔액 (`PositiveIntegerField`, 음수 불가) |

### `MileageEvent` (원장)
| 필드 | 설명 |
|---|---|
| `delta` | 증감량 (+/-) |
| `balance_after` | 처리 후 잔액 (0 이상만 허용, `CheckConstraint`) |
| `reason` | 아래 6종 중 하나 |
| `ref` | 참조 문자열 (예: `restaurant:12`, `raffle:5:x3`, `coupon:99`) |
| `idempotency_key` | **unique**. 같은 키로 재시도하면 새로 발생하지 않고 기존 이벤트를 그대로 반환 |

`reason` 종류:

| reason | 의미 | 부호 |
|---|---|---|
| `STAMP_VISIT` | 스탬프 방문 적립 | + |
| `COUPON_USE` | 쿠폰 사용 적립 (신규) | + |
| `MISSION` | 미션 보상 | + |
| `RAFFLE` | 응모권 소모 | − |
| `COUPON_EXCHANGE` | 마일리지 → 쿠폰 직접 교환 | − |
| `ADMIN` | 관리자 수동 조정 | +/− |

### `apply_delta()` 동작 방식
```
1. idempotency_key로 기존 이벤트 조회 → 있으면 그대로 반환 (재시도 안전)
2. MileageAccount row lock(select_for_update) 후 balance += delta 계산
3. delta가 음수라 balance < 0 이 되면 ValidationError(code=INSUFFICIENT_MILEAGE)
4. balance 저장 + MileageEvent 생성 (같은 트랜잭션)
```

## 2. 적립(+) 로직

### 2-1. 스탬프 방문 적립 → `credit_stamp_visit()`
- 트리거: `coupons/service.py:add_stamp()` (매장 PIN 스캔으로 스탬프 1~4개 적립) 성공 직후.
- 계산식: `base = 방문당 포인트(100) × stamp_count`, 매장이 그 주 승인된 `MILEAGE_DOUBLE` 캠페인이 있으면 `×2`.
- 월간 상한(`monthly_cap`)이 있으면 그 달 이미 적립한 금액만큼 차감한 잔여분까지만 지급 (현재 상한 없음, §4 참고).
- 스탬프 적립 자체가 실패하지 않도록, 마일리지 지급은 **SAVEPOINT로 감싸 실패해도 스탬프는 유지**된다.

### 2-2. 쿠폰 사용 적립 → `credit_coupon_use()` (신규)
- 트리거: `coupons/service.py:redeem_coupon()` → 점주가 매장에서 쿠폰을 실제 사용 처리(PIN 검증 통과)한 직후.
- 계산식: 고정 100점 (월간 상한 로직은 스탬프와 동일하게 적용됨, 매장 캠페인 배율은 적용 안 됨).
- 마찬가지로 SAVEPOINT로 감싸, 마일리지 지급 실패가 쿠폰 사용 처리 자체를 롤백시키지 않는다.
- **한 번의 흐름에서 스탬프 적립과 쿠폰 사용이 각각 별도 API 호출로 모두 일어나면, 실수로 100+100=200이 적립된다** (두 로직이 독립적으로 각각 100씩 지급하기 때문).
- 🟡 **[2026-08-30 프론트 점검 → 2026-08-31 수정]** 이 시나리오가 이론이 아니라 실제로 발생 중임을 확인했었다. 프론트 `lib/coupon/redeem_pin_dialog.dart`의 쿠폰 사용 팝업은 "스탬프도 함께 적립" 체크박스가 **기본값 ON**이었고, 제출 시 `redeemCouponWithoutThrow()`(→ COUPON_USE +100)와 `addStamp()`(→ STAMP_VISIT +100×개수)를 **한 흐름에서 순차 호출**해 기본 케이스로 100+100=**200이 적립**되고 있었다. **체크박스 기본값을 OFF로 바꿔 프론트에서는 수정했지만**, 스탬프-쿠폰 동시 적립이 애초에 의도된 정책인지는 여전히 기획 확인이 필요하다(의도라면 백엔드 쪽에서 이중 지급이 아니게 설계를 다시 봐야 한다). 상세는 §9-1 참고.

### 2-3. 미션 보상 → `missions/service.py:claim_mission()`
- 미션(`MissionDefinition.reward_mileage`)에 설정된 값만큼 지급. 미션별로 관리자가 개별 설정.

## 3. 차감(−) 로직

### 3-1. 응모권 소모(대회) → `promotions/raffles.py:enter_raffle()`
자세한 내용은 §5 참고. 요약:
- 응모 1장(티켓)당 `raffle.cost_mileage` (기본 100) 차감.
- 한 번의 요청에 `quantity`(장수)만큼 응모 가능 → `quantity × cost_mileage`를 한 번에 차감.
- 잔액 부족 시 `INSUFFICIENT_MILEAGE` → API는 409 응답.
- ⚠️ **[프론트 점검] 백엔드의 `quantity` 다수 응모 기능이 앱 UI에 전혀 노출되지 않는다.** 상세는 §9-2 참고.

### 3-2. 마일리지 → 쿠폰 직접 교환 → `coupons/service.py:exchange_mileage_for_coupon()`
- `CouponType`에 `TRIGGER_MILEAGE` 트리거가 있고 `rules_json.cost_mileage`(없으면 `mileage_face_value`)가 설정된 쿠폰 타입만 교환 가능.
- 예: `MILEAGE_MEAL_5000`(5,000P), `MILEAGE_MEAL_10000`(10,000P) → **1P = 1원 비율로 하드코딩**(마이그레이션이 직접 세팅됨). 응모(대회)와는 완전히 다른 별도 기능이며 가격 체계도 다르다.
- 🔴 **[프론트 점검] 이 기능(`POST /api/mileage/exchange/`)을 호출하거나 노출하는 화면이 프론트에 전혀 없다.** 상세는 §9-3 참고.

### 3-3. 관리자 조정 → `ADMIN`
- reason만 정의되어 있으며 `apply_delta`를 거치는 전용 관리 API는 없음. Django 기본 admin에서 `MileageEvent`/`MileageAccount`를 직접 만질 때 남기는 값으로 추정.

## 4. 설정값 (`dashboard.AdminConfig`, key-value)

| key | 기본값 | 의미 |
|---|---|---|
| `mileage_visit_points` | **100** | 스탬프 1개당 적립 포인트 |
| `mileage_coupon_use_points` | **100** | 쿠폰 사용 1건당 적립 포인트 |
| `mileage_monthly_cap` | **0 (무제한)** | 월간 적립 상한. 0이면 상한 없음 |

- `AdminConfig`는 값이 DB에 없으면 위 기본값으로 폴백한다 (`mileage/service.py:_get_admin_config_int`).
- **과거 버그**: `AdminConfig.get(key)`가 반환하는 모델 인스턴스를 `.value`가 아니라 `str(인스턴스)`로 파싱하는 버그가 있어, DB에 값을 넣어도 항상 기본값으로 폴백되고 있었다. 이번에 함께 고쳤다 → 이제 DB의 값을 넣으면 실제로 반영된다.
- 이 세 값을 조회/수정하는 전용 관리자 화면·API는 아직 없다 (진단용 `GET /api/dashboard/admin/config-debug/`로 전체 키만 조회 가능). 값을 바꾸려면 DB에 직접 `AdminConfig(key=..., value=...)` row를 넣어야 한다.

## 5. 대회(응모권 응모) 상세

### 응모 → 멀티 티켓 지원
- `POST /api/raffles/<id>/enter/`
  - body: `idempotency_key`(또는 `Idempotency-Key` 헤더, 필수) + `quantity`(선택, 기본 1)
  - **마일리지를 여러 개 써서 한 번에 여러 장 응모할 수 있다.** `quantity`장 쓰면 `RaffleEntry` 행이 그만큼 각각 생성되고, 총 `quantity × cost_mileage`가 한 번에 차감된다.
  - 응답은 `tickets`(현재까지 누적 응모 장수), `balance`(차감 후 잔액) 포함.
  - 한 유저가 한 대회를 여러 번 나눠서 응모(quantity=1을 여러 번 호출)해도 되고, 한 번에 여러 장(quantity=5)을 사도 된다 → **1인 1건 제약은 없다.**
  - ✅ **2026-08-31 프론트 반영 완료 — §9-2 참고.** 응모 카드에 수량 스테퍼를 추가하고 `enterRaffle()`이 `quantity`를 전송하도록 고쳤다. 응모 성공 후에도 버튼이 잠기지 않아 같은 대회에 계속 추가 응모할 수 있다.

### 추첨 → 균등 확률 + 티켓 수만큼 가중치
- `POST /api/dashboard/admin/raffles/<id>/draw/` (관리자 수동 실행. 자동/크론 없음)
- 알고리즘 (`promotions/raffles.py:draw_raffle()`):
  ```
  pool = 아직 안 뽑힌 유저들의 RaffleEntry.user_id 전부
         (같은 유저가 산 티켓 수만큼 pool에 중복으로 들어감)
  random.shuffle(pool)
  앞에서부터 훑어, 이미 뽑힌 유저는 건너뛰고 need명 채울 때까지 픽
  ```
  - 별도의 확률 공식(weighted random)을 쓰지 않는다. **풀 안에 자기 user_id가 몇 번 들어있는지로 확률이 자연스럽게 비례**한다 → 3장 산 사람은 1장 산 사람보다 당첨 확률이 3배 더 높다.
  - 같은 회차에서 한 유저가 두 번 당첨되지 않도록 중복 제거 처리(`RaffleWinner`에 `UniqueConstraint(raffle, user)`도 걸려 있어 이중 안전 장치).
  - `winner_count`를 나중에 늘리고 다시 추첨하면, 이미 당첨된 사람을 제외하고 부족분만 추가로 뽑는다(즉시 재추첨).

### 당첨 후
- 당첨자마다 `prize_amount`(5,000/10,000원)에 대응하는 식사권 쿠폰이 자동 발급(멱등 키로 중복 발급 방지).
- 카카오 알림 발송, 앱 진입 시 유저 본인 당첨을 보여주는 팝업 API(`GET/POST /api/raffles/win-popups/`).
- 발급된 쿠폰은 발급 시점 특정 식당에 묶이지 않고, 제휴 식당 어디서든 PIN으로 사용하면 그 식당이 기록된다.

### API 요약

| 대상 | Method | Path | 설명 |
|---|---|---|---|
| 유저 | GET | `/api/raffles/` | 응모 가능한 대회 목록 (`my_tickets`로 내가 산 장수 표시) |
| 유저 | POST | `/api/raffles/<id>/enter/` | 응모 (`quantity`로 여러 장 가능 — ✅ 프론트 반영 완료, §9-2) |
| 유저 | GET | `/api/raffles/my/` | 내 응모 내역 (대회 단위로 티켓 합산해서 반환) |
| 유저 | GET/POST | `/api/raffles/win-popups/` | 신규 당첨 팝업 조회/확인 |
| 유저 | GET | `/api/raffles/redeem-restaurants/` | 당첨 쿠폰 사용 가능 제휴 식당 |
| 관리자 | GET/POST/PATCH | `/api/dashboard/admin/raffles/` | 대회 생성·수정·조회 (`cost_mileage` 응답 시 100 기본) |
| 관리자 | POST | `/api/dashboard/admin/raffles/<id>/draw/` | 추첨 실행 |
| 관리자 | GET | `/api/dashboard/admin/raffles/<id>/winners/` | 당첨자 목록 |

관리자 응답에는 `entry_count`(판매된 티켓 총량)와 `participant_count`(고유 응모자 수)가 분리되어 내려간다 → 한 유저가 여러 장 사면 이 두 값이 다를 수 있다.

## 7. 전체 흐름 요약

```
[적립]
  스탬프 PIN 적립 성공 → credit_stamp_visit() → apply_delta(+100 × count [×2 캠페인], STAMP_VISIT)
  쿠폰 매장 사용 성공  → credit_coupon_use()  → apply_delta(+100, COUPON_USE)
  미션 클레임         → claim_mission()       → apply_delta(+reward_mileage, MISSION)

[차감]
  대회 응모(quantity장) → enter_raffle()              → apply_delta(-100×quantity, RAFFLE) → RaffleEntry × quantity 생성
  마일리지 쿠폰 직접교환 → exchange_mileage_for_coupon() → apply_delta(-cost, COUPON_EXCHANGE) → 쿠폰 발급

  모든 경로는 apply_delta()를 거치며:
    idempotency_key 중복 방지 → row lock → balance 갱신 → MileageEvent(원장) insert
    (동일 DB 트랜잭션, 잔액 음수 방지 CheckConstraint)

[추첨]
  관리자가 수동으로 draw_raffle() 실행
    → 응모 풀(티켓 수만큼 중복 포함)에서 균등 확률로 need명 픽 (같은 유저 중복 당첨 방지)
    → 당첨자에게 식사권 쿠폰 자동 발급 + 알림
```

## 8. 주의사항 / 알려진 특이사항

- **`redeem_coupon()`의 트랜잭션 alias 불일치**: 함수 데코레이터는 `@transaction.atomic`(alias 미지정 → `default` DB 기준)인데, 실제 쿼리는 라우터로 얻은 `cloudsql` alias를 쓴다. 이 함수 내부의 원자성 보장이 실제 쓰기가 일어나는 DB와 다를 수 있는 기존 구조적 이슈이며, 이번 마일리지 작업 범위에서는 손대지 않았다 (마일리지 적립 호출 별도로 올바른 alias의 SAVEPOINT로 감싸짐).
- **월간 상한 = 0은 "무제한"**을 의미한다. 관리자가 추후 상한을 걸고 싶으면 `AdminConfig(key="mileage_monthly_cap", value="5000")` 같은 row를 추가하면 된다.
- **`docs/마일리지_응모_당첨_상품권.md`는 이번 변경 이전 문서**라, "응모 시 유저 잔액 차감·환급 없음" 같은 서술이 지금은 맞지 않는다(지금은 응모 시 마일리지가 차감된다). 이 문서(현재 문서)가 최신 기준이다.

## 9. 프론트엔드(Flutter, `new1` 레포) 연동 점검 결과 (2026-08-30 점검 / 2026-08-31 수정)

이 백엔드 문서를 프론트엔드 코드(`lib/services/mileage_service.dart`, `lib/mileage/*.dart`, `lib/coupon/redeem_pin_dialog.dart` 등)와 대조해 발견한 4건 중 3건을 2026-08-31에 프론트 코드로 직접 수정했다. 나머지 1건(§9-3, 신규 화면)은 기획 확정 후 별도 작업으로 남겨뒀다.

### 9-1. ✅ 수정 완료 — 쿠폰 사용 이중 적립(§2-2) 기본값을 껐다
- **문제였던 것**: `lib/coupon/redeem_pin_dialog.dart`의 쿠폰 사용 PIN 팝업에서 "스탬프도 함께 적립" 체크박스가 **기본 ON**이라, 제출 시 `redeemCouponWithoutThrow()`(COUPON_USE +100)와 `addStamp()`(STAMP_VISIT +100×개수)가 같은 흐름에서 순차 호출되어 기본 케이스로 **100+100=200**이 적립되고 있었다.
- **수정**: `_addStamp` 기본값을 `true → false`로 변경했다. 이제 쿠폰 사용만 하면 COUPON_USE 100만 적립되고, 점주가 방문 스탬프도 함께 인정해줄 때만 사용자가 체크박스를 직접 켜서 STAMP_VISIT을 추가로 적립받는다.
- ⚠️ 이건 "이중 적립을 막는 가장 보수적인 기본값"을 고른 것이지, 스탬프-쿠폰 동시 적립이 애초에 의도된 정책이었는지는 별도로 기획 확인이 필요하다. 만약 "쿠폰 사용 시 스탬프도 항상 함께 적립되는 게 맞다"는 결론이 나면, 이번 수정과는 반대로 프론트가 아니라 **백엔드에서 두 reason 중 하나만 지급**하도록 고치는 게 맞다(프론트 체크박스로 이중 지급 여부를 좌우하는 건 임시방편에 가깝다).

### 9-2. ✅ 수정 완료 — 대회 "여러 장 응모"(quantity) 지원
- **문제였던 것**: `enterRaffle()`이 `quantity` 파라미터를 아예 안 보냈고, 응모 버튼은 성공 후 영구 비활성화되어 대회당 평생 1장만 살 수 있었다.
- **수정**:
  - `Raffle` 모델에 서버가 내려주는 `my_tickets`(§5 API 요약 표에 있던 필드, 기존엔 파싱 안 됨)를 추가해 "내가 이 대회에 몇 장 샀는지"를 정확히 표시하게 했다.
  - `MileageService.enterRaffle()`에 `quantity` 파라미터를 추가해 body에 실어 보낸다.
  - `mileage_shop_screen.dart` 응모 카드에 1~20장 수량 스테퍼(`-` / `N장` / `+`)를 추가했고, 확인 다이얼로그와 버튼 문구에 `수량 × 단가` 총액을 표시한다.
  - 응모 성공 후에도 버튼을 잠그지 않아, 같은 대회에 계속 추가 응모할 수 있다(수량은 다음 구매를 위해 1로 리셋).
  - 멱등 키는 여전히 구매 1건당 하나씩 새로 발급하고, 성공 시에만 제거한다(네트워크 실패 시 재시도는 같은 키 재사용).

### 9-3. ⏸️ 보류 — 마일리지 → 쿠폰 직접 교환(§3-2) 기능이 프론트에 없음
- `lib/` 전체에서 `POST /api/mileage/exchange/`를 호출하는 코드나 화면이 여전히 없다.
- 화면 진입 지점, 교환 가능 쿠폰 목록 표시 방식, 카피 등 프로덕트 결정이 필요한 신규 기능이라 이번 수정 범위에서는 제외했다(사용자 확인 후 별도 진행하기로 함). 필요해지면 §3-2/§6을 기준으로 (a) 교환 가능 쿠폰 타입 조회 → (b) 확인 다이얼로그 → (c) `POST /api/mileage/exchange/` 호출 → (d) 결과를 쿠폰함에 반영하는 흐름으로 구현한다.

### 9-4. ✅ 수정 완료 — 마일리지 이력 화면 reason 라벨 매핑
- `lib/services/mileage_service.dart`의 `MileageEvent.label` 폴백 스위치문에 `STAMP_VISIT`(→ 방문 적립, 기존 `VISIT`도 하위 호환으로 유지), `COUPON_USE`(→ 쿠폰 사용 적립), `COUPON_EXCHANGE`(→ 쿠폰 교환 사용) 케이스를 추가했다.
- 이제 서버가 `memo` 없이 reason만 내려주는 이벤트도 의미 있는 한글 라벨로 표시된다.
